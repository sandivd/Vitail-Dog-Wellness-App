## Purpose and scope

Vitail helps dog owners build regular walking habits, understand daily progress, discover dog-friendly places and use earned points for rewards. This page replaces broad journey statements with small, testable user stories and keeps implementation choices in the architecture documentation.

The primary actor is an authenticated dog owner or authorised co-owner. A partner staff member participates in in-person reward use. The proposed MVP baseline uses one dog profile per user; co-owner access is a separate capability. Multi-dog scope is disputed and remains subject to OI-01 in the Decision Log.

**Evidence status:** The feature intent comes from the linked Confluence sources. The story decomposition, IDs, consolidated priorities and detailed acceptance criteria below are proposed refinements, not historical client sign-off. Explicitly recorded business rules are identified through the traceability table. Open rules must be resolved before dependent stories can be accepted. No row asserts that a feature has passed testing.

**Priority:** Must = required for the proposed core MVP; Should = valuable but negotiable; Could = optional enhancement. These priorities are recommendations for baseline review, except where sources expressly identify optional scope. Keep Jira delivery status separate from requirement priority.

## Core user stories

Each numbered criterion can be referenced as `US-xx-ACn` in test records. Criteria cover observable outcomes; implementation mechanisms belong in technical design.

| User story ID | User story | Priority | Acceptance criteria |
|---|---|---|---|
| US-01 | As a dog owner, I want to register and sign in with email/password or Google so that I can securely access Vitail. | Must | 1. Valid registration/sign-in opens onboarding or the linked dog profile as appropriate. 2. Invalid credentials or cancelled Google sign-in do not create an authenticated session and show a recoverable outcome. 3. Both supported methods are tested; restricted Google test-user access is documented until production readiness is confirmed. |
| US-02 | As a returning owner, I want session continuity, password recovery and logout so that I can regain and control account access. | Must | 1. Reopening the app preserves a valid session under the approved session policy. 2. Email/password users can complete password reset; old credentials then fail. 3. Logout prevents access to protected data until sign-in. Session lifetime remains to be confirmed. |
| US-03 | As a new owner, I want to create my dog's profile so that Vitail can personalise the experience. | Must | 1. The form captures the agreed dog attributes, including name, breed/size, age, dog activity level and health information. 2. Missing required or invalid inputs are identified before saving. 3. Saving creates one persistent profile and its share identifier. 4. Explicitly skipping microchip details permits onboarding and tracking. Field mandatory/optional definitions require baseline approval. |
| US-04 | As an owner, I want to view and edit my dog's details and photo so that the profile remains accurate. | Must | 1. Saved details appear after reopening the profile. 2. Valid edits persist; invalid edits leave existing data intact and show an error. 3. Photo upload failures are recoverable. 4. Changes to recommendation inputs trigger recalculation under the approved goal-change policy. |
| US-05 | As an authorised co-owner, I want to join an existing dog's profile so that we share its care records. | Must | 1. A signed-in user can use the approved code and authorisation flow to link to the existing profile without creating a duplicate dog. 2. Invalid codes and unauthorised requests do not expose dog data. 3. Authorised users see the same persisted activity and reward state. Approval, roles and revocation rules are blocked by OI-06. |
| US-06 | As an owner, I want to provide a correctly formatted microchip number so that the app can assess reward eligibility. | Must | 1. Number-entry submission accepts exactly 15 digits and rejects shorter, longer or non-digit values. 2. The value remains a string so leading zeroes are preserved. 3. Explicit skip remains available for non-reward use. 4. Success is described as format acceptance, not registry or ownership verification. Prefix and certificate rules remain OI-02. |
| US-07 | As an owner, I want a personalised daily walking time and distance goal so that I have a clear activity target. | Must | 1. The app displays time and distance from a versioned, approved rule set and the saved dog inputs. 2. Activity level refers to the dog. 3. Selected health severity affects the result according to an approved mapping. 4. Worked input/output examples pass, including missing or unsupported input handling. 5. General-wellbeing guidance is distinguished from veterinary advice. Numerical rules are blocked by OI-04. |
| US-08 | As an owner, I want a daily dashboard so that I can see progress and begin a walk quickly. | Must | 1. Home shows the dog's name/photo, daily goal, recorded progress and today's points. 2. A prominent Start a Walk action opens tracking. 3. A saved walk updates progress and points consistently with history and wallet. 4. No-history state shows zero progress without errors. |
| US-09 | As an owner, I want to start and monitor a walk so that my dog's activity is recorded. | Must | 1. Starting with location permission creates one active walk for the selected MVP dog. 2. Active duration, distance and route are displayed. 3. Permission denial or unavailable location produces an explanation and recovery path without fabricated tracking data. 4. Repeated Start actions do not create duplicate active sessions. |
| US-10 | As an owner, I want to pause and resume a walk so that breaks do not count as active walking. | Must | 1. Pause visibly changes the session state and stops accumulating active time and distance. 2. Resume continues the same walk. 3. Repeated pause/resume actions preserve the recorded data. This active-time interpretation is proposed for confirmation. |
| US-11 | As an owner, I want to finish and save a walk so that I can review its outcome. | Must | 1. End stops tracking and displays distance, active duration and awarded points. 2. The saved walk is visible in history after reopening the app. 3. A failed save is shown as pending/failed with a retry path. 4. Retrying does not create an extra walk or point award. |
| US-12 | As an owner, I want eligible walks to earn points so that regular activity is rewarded fairly. | Must | 1. Completed activity earns the amount calculated by the approved points rule. 2. Ineligible activity produces no award and has a clear reason. 3. Duplicate submissions do not award twice. 4. The same shared-dog activity is not multiplied by the number of co-owners. Formula, caps and concurrent activity handling remain OI-03/OI-06. |
| US-13 | As an owner, I want to see my points balance so that I know which rewards I can afford. | Must | 1. The wallet shows the persisted balance for the approved dog/account ownership model. 2. Confirmed awards and reward deductions reconcile with that balance. 3. Reopening or refreshing does not change it without a recorded transaction. 4. Failed transactions do not partially alter the balance. Wallet ownership and deduction timing remain OI-03. |
| US-14 | As an owner, I want my streak to reflect daily walking progress so that consistent activity is recognised. | Must | 1. Under the proposed synthesis, eligible daily walking time of at least 80% of the time goal qualifies; below 80% does not. 2. Reaching the threshold increases the streak no more than once per day. 3. Distance alone does not qualify a day when the time threshold is unmet. 4. Multiple saved walks aggregate under the approved day policy. Timezone, rest days and goal edits remain OI-05. |
| US-15 | As an owner, I want to browse rewards and their terms so that I can choose a suitable offer. | Must | 1. Catalogue entries show the offer, partner, points cost and applicable conditions. 2. Selecting a reward opens its details. 3. Viewing alone does not spend points or consume a reward. 4. Unavailable and empty states are clear. |
| US-16 | As an eligible owner, I want to exchange points for a reward so that I can use the benefits earned by walking. | Must | 1. An explicit confirmation checks eligibility, availability and sufficient points on the server. 2. Success creates one reward entitlement and applies exactly one approved deduction. 3. Ineligible or insufficient-balance attempts explain the issue without spending points. 4. Repeated or concurrent requests cannot duplicate the exchange. Lifecycle and microchip/certificate details remain OI-02/OI-03. |
| US-17 | As an owner, I want to present an acquired reward for in-person use so that the partner can complete it deliberately. | Must | 1. The reward clearly shows its current usability. 2. Completion requires the agreed deliberate swipe by the approved actor; merely viewing it has no effect. 3. A successful use is persisted once and cannot be reused. 4. Used/expired rewards cannot be completed again. Partner verification, terminology and lifecycle remain OI-03. |
| US-18 | As an owner, I want to view my acquired and used rewards so that I understand what remains available. | Must | 1. Acquired and used rewards are distinguishable. 2. Expiry is displayed only from an approved rule and stored entitlement state. 3. Reopening preserves the recorded state. 4. The interface clearly distinguishes viewing, acquiring and using. Expiry duration and refund handling remain OI-03. |
| US-19 | As an owner, I want to discover nearby dog-friendly venues so that I can choose useful walking destinations. | Must | 1. Explore shows available nearby venue locations and matching cards. 2. A venue opens details including name, category, address, description, partner status and any available reward. 3. Missing location permission, no results and unavailable venue data have clear states. 4. Data source, distance definition and freshness policy are agreed before acceptance. |
| US-20 | As an owner, I want to review walk history so that I can understand my dog's activity over time. | Must | 1. Saved walks show date, duration and distance in a consistent order. 2. Opening a walk shows its saved summary and available route. 3. Only authorised users can access the dog's history. 4. An empty history offers a clear starting point. |

## Additional and optional stories

These rows preserve documented ideas without silently expanding the committed MVP. Resolve the named dependencies before sprint selection.

| User story ID | User story | Priority | Acceptance criteria |
|---|---|---|---|
| US-21 | As an owner, I want tracking to survive temporary network loss so that poor reception does not lose my walk. | Should — disputed | 1. GPS samples and walk state are saved locally during an offline test. 2. Reconnection synchronises the walk once and awards points once. 3. Pending sync is visible. 4. Screen-lock and restart scenarios meet the approved lifecycle matrix. Architecture says Should; NFRs describe a stronger requirement. Resolve OI-07. |
| US-22 | As an owner, I want limited adjustment of my recommended goal so that it remains suitable without trivialising progress. | Should | 1. Changes are restricted to approved bounds and persisted. 2. Values outside those bounds are rejected. 3. Goal edits follow an agreed streak policy. The client's ±5% is an example, not an approved exact limit; resolve OI-04/OI-05. |
| US-23 | As an owner, I want to submit a microchip certificate so that I can use an alternative identity-document route. | Should | 1. Supported document types and size limits are stated. 2. Accepted uploads have a visible processing/review status. 3. Unreadable documents produce a recoverable error. 4. Upload alone does not imply verified ownership. Document review and reward eligibility remain OI-02. |
| US-24 | As an owner, I want a Care Score so that I can understand longer-term care progress. | Could | 1. A selected, versioned specification defines inputs, weighting, time window and missing-data behaviour. 2. Reference examples reproduce the displayed result. 3. The score is presented as general wellbeing feedback. The attached specification must be reviewed before this story is baselined; no weights are assumed here. |
| US-25 | As an owner, I want to control walking reminders so that notifications suit my routine. | Should | 1. Users can enable/disable reminders. 2. OS permission denial is handled. 3. Disabled reminders do not fire. 4. Approved schedules avoid duplicate reminders. Exact reminder triggers remain OI-09. |
| US-26 | As an owner, I want optional shared-walk point boosts so that walking alongside others is encouraged. | Could | 1. Eligibility, consent, detection and boost rules are approved before development. 2. One eligible event receives the approved boost once. 3. Ineligible or duplicate events do not receive extra points. Explicitly optional in the client questionnaire. |
| US-27 | As an owner, I want weather-aware activity guidance so that recommendations account for relevant conditions. | Could | 1. A reliable weather source and approved adjustment rules are selected. 2. Tested conditions produce the approved guidance. 3. Unavailable or stale weather data is disclosed and handled using an agreed fallback. No temperature threshold is invented here. |

## Scope reconciliation and acceptance process

1. **Preserve persona material as context.** The existing [User stories](https://poodles.atlassian.net/wiki/spaces/poodles/pages/9961487) describes Morgan, Olivia and Maddie at journey level. Link those journeys to these smaller stories; do not treat Morgan's two-dog scenario as proof of approved MVP scope.
2. **Resolve contradictory details.** Correct 16-digit microchip wording to the confirmed 15-digit rule. Distinguish time-based streak qualification from distance progress. Confirm multi-dog scope, offline priority, reward lifecycle and formula limits through the Decision Log.
3. **Approve a baseline.** Review the proposed priorities, field definitions and acceptance criteria with the team and client. Record actual reviewer names, review date and approved version only when review occurs.
4. **Link delivery evidence.** Add the stable story ID to the relevant Jira item and test record. Test outcomes reference individual criteria, such as US-06-AC1. A feature update in meeting minutes is progress evidence, not an acceptance-test pass.
5. **Accept only demonstrated behaviour.** A story is ready for acceptance when dependent open rules are resolved, criteria pass on supported devices, defects are addressed or explicitly accepted, and the designated reviewer records the result. Optional stories enter a sprint only after scope approval.

**Review boundary:** This is a source-linked synthesis of relevant readable Confluence documentation, not a claim to have audited every workspace artifact or verified the running app. Detailed criteria that extend broad source wording are explicitly proposed quality improvements. No assessment mark can be guaranteed; the structure directly addresses the recorded supervisor feedback.
